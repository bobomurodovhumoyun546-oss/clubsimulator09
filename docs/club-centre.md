# Club centre: implementation and operating notes

## Delivered systems

The existing React/Vite, Three.js/Phaser and Express/libSQL architecture is retained. The new **Club centre** tab contains nine working sections in Uzbek, Russian and English. All players are existing catalogue/card IDs. Existing club saves, formations, gifts, packs and accounts are preserved.

1. **Advanced tactics**: existing ten formations (including 4-3-3, 4-2-3-1, 4-4-2 and 3-5-2), touch/pointer drag positions, keyboard-accessible coordinate fields, starting-player swaps, captain, five role assignments, seven tactical sliders and eight presets. Server checks ownership, identity uniqueness, positional eligibility, bounds and captain. Width, line, mentality, pressing, tempo, transition, passing and fatigue connect to the existing 11v11 engine. Tactical familiarity grows by two per recorded match and falls when changing setups. No guaranteed-win tactic.
2. **Stadium**: name, seat colour, climate and ticket price; stands/capacity, lights, pitch, VIP and shop upgrades. Five-level caps, increasing costs, 1–5 minute construction, prerequisite stands for VIP/shop, cancellation with 75% refund, history and collection. CSS preview is a stadium illustration; saved seat colour also reaches the actual Three.js match. Attendance, operating share of ticket revenue, facility income and player wages are recorded per career match.
3. **Transfers**: server-valued catalogue with search, positions, price/rating/name sort, 24-player pages, shortlist, paid scouting report and daily career-market trends. Prices use ability, known age, modeled potential, recorded form, existing injuries, demand and contract time. Unknown age is neutral in valuation; the displayed potential range is explicitly an estimate, not a new EA statistic. Three AI counterpart clubs have finite budgets and squad-role needs. Bids, counters, acceptance/rejection, one-day expiry, bonuses, wages, renewal, sale and transfer history are persisted. One identity per career roster; simultaneous acceptance cannot duplicate a purchase.
4. **Missions**: four suitable missions per account/day, generated deterministically. Progress comes only from persisted server match/skill events. Midnight Asia/Tashkent reset, live countdown, bounded coin reward and XP, exactly-once claims.
5. **Competitions**: 4/5/8 teams, home-and-away league, single round robin, groups plus knockout and cups. Odd-team byes, saved fixtures, AI rounds, points/goal difference/goals-for tiebreakers, standings, brackets, extra time and penalties, prizes and trophy cabinet. Match simulation uses the same engine as 3D play. Scorer screens include available recorded player events; CPU-only fixture scorelines do not fabricate named scorers.
6. **Goal of the match**: recorded scorer, assist, minute, origin/target, distance, shot type, difficulty and decisive context when available. Rating: distance up to 35 points + difficulty up to 30 + shot type up to 20 + assist up to 8 + decisive context up to 7, capped 0–100. Own goals are ineligible. Highest score wins, earliest minute breaks ties. No eligible goal is explicitly handled. Gallery provides a 2D SVG event reconstruction, not video or an exact 3D replay; missing coordinates are reported instead of fabricated. Reduced-motion mode disables the animated flight.
7. **Weather**: seeded season/climate forecast, clear/rain/snow/wind/fog/hot. Passing, shooting, grip/visibility indicators and stamina modifiers stay small. Rain/snow particles and fog run in Three.js; low graphics reduces particle count, reduced motion disables weather particles and celebration camera motion. Match settings include all six types. Stadium climate influences forecasts.
8. **Skills**: ten-round penalty, curved free kick, passing accuracy, path-based dribbling and shooting targets. Mouse/touch, WASD/arrows plus Enter, timers, difficulty, score feedback and history. Server validates coordinates, current round, timing, curve/path conditions and calculates scores; it never trusts a submitted score. First three completed attempts per Tashkent day can pay; ten starts/day maximum. Input automation is not claimed to be impossible; rewards remain bounded.
9. **Career**: recorded matches/results/goals/assists/clean sheets, transfers, income/spending, records, trophy cabinet, player totals, season/competition filters, recent-result chart and comparison. Legacy totals are shown separately as a source snapshot. Unknown historical events are not invented.

## Persistence and financial boundary

Additive migration in `accountSchema.js` creates `career_states(user_id PRIMARY KEY REFERENCES users, state JSON, revision, updated)` and an updated index. The JSON contains versioned domain models: roster/contracts, tactics/presets, stadium/construction/history, market/AI/offers, competitions/fixtures, match events/highlights, missions, skill sessions, event ledger and command receipts. Domain changes, finances and the receipt are committed together in one SQL compare-and-swap update. Retry reloads resolve concurrency, while the stable command ID deduplicates repeat submissions across separate Vercel function instances. Request-body account IDs, balances, scores and rewards are ignored; identity comes from the authenticated session. Receipts are not pruned and their IDs cannot be reused with a different payload. Safe bounds: 10,000 commands/events, 1,000 matches, three active competitions, eight presets and 20 career matches/day.

**Career starts with a separate server-issued 250,000 budget.** It imports the existing squad, prioritizing the starting XI's edition when multiple cards share an identity. It does not debit, reset or treat the older client-editable club wallet as authoritative. Career transfer ownership belongs to this roster. The hub's 3D practice match uses that roster and the same tactics/weather but earns no career prizes, because browser-submitted final scores are not authoritative. Reward-eligible career matches are simulated by the server. This boundary is explicit in the interface. Legacy manual matches and their previous rewards are unchanged; this release does not claim to make the legacy client economy tamper-proof.

A career match advances one career calendar day; transfer windows are days 1–14 and 46–59 of each 90-day cycle. Construction, daily missions, offer expiry and contract deadlines use server wall time. A modeled contract year equals 12 real days; starting contracts last 24 real days. Wages are charged per recorded match. Server-seeded AI rounds can be recomputed deterministically, while completed fixture IDs and command receipts prevent repeated rewards.

## 3D match changes and face resources

Goals now keep a 3.6-second celebration at the scoring location, pause football time, frame the scorer smoothly, show the scorer's actual name at the bottom and resume the correct kickoff once. Four identity-stable poses are animated. Pause, reduced motion and multiplayer state snapshots are respected. Keeper rushing aims at the actual ball/interception lane in either half; strong AI keepers may close down danger. Maximum 110 OVR has 70% ordinary / 85% rushing **conditional save probability for a reachable shot**; near-post shots have at least an 80% save chance. These are not guarantees that 70% of every possible whole-match shot will be saved, because interception geometry still matters.

`portraitFace.js` wraps the existing player's local portrait around the front of the animated head. `portraitFaces.json` stores automatically detected UV bounds and a sampled skin colour, without modifying the original image. `scripts/analyze-portrait-faces.py` uses OpenCV's YuNet ONNX model from the [official OpenCV Zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet); its MIT license is retained in `scripts/resources/YUNET-LICENSE.txt`. It is an offline analysis tool, not a runtime or production dependency.

This is a photographic front-face layer, **not a scanned head or verified 80% likeness**. Detection does not verify identity, scan the sides/back or prove perceptual similarity. Source photos without reliable faces retain a source crop, and records without any portrait retain the procedural fallback. To meet a measurable 80% resemblance requirement from every angle, identity-specific licensed rigged heads/multi-view scans and a defined review metric are still required. No new player database or fabricated likeness score was introduced.

## Verification

Unit and integration coverage includes tactical tradeoffs, weather determinism, valuations, standings/byes, mission timezone/reset, goal ratings, event deduplication, construction/refunds, transfer races, invalid budgets, score forgery, bounded skill rewards, fixture finalization, authorization and two independent libSQL instances. Existing match/rules/keyboard/OVR/packs/save tests remain required. Browser QA uses an isolated SQLite account server, never real production accounts. All nine tabs, a competition round, a skill input, desktop and 390px mobile layout were exercised. The 3D portrait was visually inspected with real WebGL rendering. Live deployment is checked separately after publishing.
